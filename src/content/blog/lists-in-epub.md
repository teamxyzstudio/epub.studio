Lists in EPUB fail in a way that looks petty until it is your book: bullets vanish, a numbered list restarts at 1 halfway through, a list arrives as bullets when it left as numbers — or one line shows a bullet *and* a number, side by side. The complaints run back well over a decade on MobileRead — vanished bullets the thread blames on reader CSS support, double bullets after a Calibre conversion, numbering that cannot resume after an interruption — and the same shapes turn up on the Literature & Latte forum (bullets that came out as numbers) and in a LibreOffice bug about lists that render fine in PDF export but lose their markers in EPUB export.

Different tools, same confusion underneath. Every one of those symptoms follows from a single fact about how HTML — and therefore EPUB — stores a list: **the bullet is not in your text, and neither is the number.**

## The marker is never in your text

A list in an EPUB chapter is three tags: `<ul>` for a bulleted list, `<ol>` for a numbered one, `<li>` for each item. What is *inside* the tags is only the item's own words. The `•` and the `3.` exist nowhere in the file — the reading engine generates them at render time, from the markup. The CSS Lists specification says this in one line: [list items generate `::marker` pseudo-elements; no other elements do](https://www.w3.org/TR/css-lists-3/) — the marker is a generated box the engine attaches beside the item, with a counter it increments itself.

We can show that on a real file rather than asserting it. A 329-byte Markdown packing checklist went through our live Markdown converter and came out as a 2,787-byte EPUB. Here is the chapter it produced, rendered at reading size:

Now the part worth a double-take. Search that chapter's body for the characters you can see on screen and they are not there: no `•`, no `1.`, no `2.`. The only digit in the entire body is the 4 in `start="4"` — an attribute, an instruction to the renderer, not text a reader is shown. Five visible numbers, zero stored ones.

That is the mechanism behind every symptom in the opening paragraph. Markers that are generated can be *not* generated — by markup that got lost in conversion, or by styling an engine cannot follow. And markers that were baked into the text as ordinary characters answer to nobody: they cannot renumber, cannot restyle, and happily stack up next to a generated marker on the same line.

## Made properly, a list carries everything — even a resumed count

The packing fixture was built to hit the classic trouble spots: a nested sub-item, and a numbered procedure interrupted by a paragraph of prose. The converted markup handled both:

```
<ol>
<li>Clear the ground</li>
<li>Peg the groundsheet</li>
<li>Thread the poles</li>
</ol>
<p>Stop here if rain is forecast before the inner goes up. …</p>
<ol start="4">
<li>Clip the inner tent</li>
<li>Peg the guylines</li>
</ol>
```

The interruption necessarily ends the list — markup cannot thread one list through a foreign paragraph — but the second list opens with `start="4"`, so the rendering picks up exactly where the count left off, as the screenshot shows. That number comes from the source: Markdown's own rule is that [the start number of an ordered list is determined by the list number of its initial list item](https://spec.commonmark.org/0.31.2/#start-number), so typing `4.` on the resumed item is all it takes. One of the oldest MobileRead complaints in this family — EPUB lists cannot resume after an interruption — describes an EPUB 2-era ceiling; the attribute is ordinary HTML and our converter emits it today.

Word documents arrive just as cleanly, because DOCX stores real list structure. We hand-built a 1,753-byte DOCX with one bulleted and one numbered list, properly defined in its numbering tables, and the live [DOCX converter](/docx-to-epub) delivered `<ul>` for the bullets and `<ol>` for the steps — a 2,689-byte EPUB with both lists intact as markup.

## Where lists die on the way in

Plain text is the other story, and it is where a lot of "my bullets disappeared" reports actually begin. A `.txt` file has no list structure to carry — a dash at the start of a line is a dash, nothing more. Our plain-text importer splits paragraphs on blank lines and joins single line breaks into spaces, which is the standard reading of prose. Type a list the way everyone types a list — one item per line — and this is what the typed markers turn into:

```
<p>- tent - groundsheet - head torch</p>
<p>1. Clear the ground 2. Peg the groundsheet 3. Thread the poles</p>
```

One run-on paragraph per list, typed markers embedded mid-sentence. We ran exactly that fixture through the live [plain-text converter](/txt-to-epub) to get those lines. It is not a bug in any one tool so much as the honest limit of the format: the converter was handed characters, not structure, and single newlines are fold points in prose. Blank-line discipline — an empty line between items — at least lands each item in its own paragraph. But no plain-text route produces a `<ul>` or `<ol>`, which means no renumbering, no nesting, no hanging indent, ever. If the list matters, the source needs a format with a list channel: Markdown costs exactly one `-` per line and keeps everything.

## Where lists die on the way out

Conversion *out* of EPUB is where good lists get flattened — and our own tools are the demonstration, so this section is also an honest-limits note about them. The extractor that feeds our EPUB-to-text, EPUB-to-Word and EPUB-to-PDF tools reads each chapter into a flat sequence of blocks, and its list handling keeps each item's text while dropping the one bit that distinguishes a numbered list from a bulleted one — all items become the same generic kind, and nesting is flattened with them. Downstream, every exporter then draws the same marker for everything:

| Route | What the packing list became |
|---|---|
| [EPUB to text](/epub-to-txt) | Every item prefixed `- `, ordered and unordered alike; the 1–5 numbering gone; the nested sub-item reduced to a bare unmarked line |
| EPUB to Word | Every item a bulleted paragraph — the 8,794-byte output's numbering table defines only a bullet format, so the numbered procedure arrives as bullets |
| EPUB to PDF | Every item drawn with the same `•`, the numbered ones included |

Those are live results from round-tripping the same packing.epub, not a reading of the code — though the code agrees, and we have logged the ordered/unordered distinction as a fix worth making. The deeper point survives any one tool's improvement: the numbers were generated, so any exporter that leaves list markup behind has nothing to copy. Plain text has no markers to generate; something has to be synthesised, and what gets synthesised is a bullet. It is the same flattening we documented for [tables in EPUB](/blog/tables-in-epub), hitting a humbler structure.

The notorious historical version of this is the exporter that goes the other way and *bakes the markers in*: InDesign's EPUB export, for years, wrote automatic list numbering into the text as ordinary characters. Those numbers survive everything — and answer to nothing. They cannot renumber when an item is added, and if the paragraphs later end up inside real list markup, the engine generates its marker next to the baked-in one. That is the bullet-plus-number line, two layers each doing their job.

## The reader's share of the blame

One symptom in the opening list is not a conversion fault at all. Threads about bullets that show in one app and vanish in another usually end — as a long-running MobileRead thread does — at the book's own stylesheet: publishers restyle markers by suppressing the defaults (`list-style-type: none`) and redrawing them with `::before` content and CSS counters, and a reading engine with partial CSS support executes the suppression but not the redraw. The default markers would have rendered everywhere; the clever ones rendered nowhere. We cannot put an e-ink device on the bench in this test environment, so we pass those reports along as reports — but the mechanism is the same one in the spec passage above: markers live or die by what the engine generates. The less a list asks of CSS, the fewer places it can fail.

The through-line for authors is short. Keep lists as markup for as long as the pipeline allows, and let markers be generated rather than typed. If your source is plain text, give it a list channel before converting: one dash per item in a file saved as `.md`, dropped on the [Markdown converter](/markdown-to-epub), comes out the other side with bullets, numbering, nesting and even a resumed count — all of it stored the way a list should be stored, which is to say: not at all, until a reader opens the page.
